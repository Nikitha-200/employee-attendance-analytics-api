# DECISIONS.md  (about 150-200 words in total - plain language, your own words)

1. **Indexes.** A unique `employees.emp_code` index guarantees that employee codes cannot race into duplicates. A unique `(emp_code, date)` index gives the attendance natural key and makes punch-in race-safe. The date/employee sort index supports attendance listing; `(emp_code, date)` supports per-employee month filtering; `(department, joined_on)` supports department headcount lookups. I considered indexing every derived field for analytics, but these endpoints group over a period, so more single-purpose indexes would cost writes without helping their leading filters.
2. **Punch-in race.** Both requests can pass the employee lookup, but they insert the same `(emp_code, date)`. MongoDB's unique index commits one insert; the other raises `DuplicateKeyError`, which the API translates to 409.
3. **Ties.** `$rank` gives tied employees the same rank and skips the next rank. Filtering rank `<= limit` after ranking returns every tied row at the cutoff; sorting then uses employee code for stable display order.
4. **Headcount.** The aggregation starts with eligible employees and looks up each employee’s attendance logs for the month. It does not unwind the logs array, so employees with no matching logs remain in the pipeline with an empty array and still contribute one to headcount.
5. **At 100x.** I would partition the analytics workload by month or maintain incremental daily summaries, then validate the write and consistency tradeoff. The raw attendance collection would remain the source of truth.
